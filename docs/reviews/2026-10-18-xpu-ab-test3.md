# Intel XPU 隔離比較：2.30-tw.2-test.3

日期：2026-10-18（Asia/Taipei）｜ChatGPT

本輪授權是官方新版 PyTorch 與 comfy-kitchen-xpu 整合測試分支、不同啟動方式、互不改寫執行環境。基準 neo-test：91d3ab52cdc8f259361a64f438c8f801d866f8e5。正式 neo／正式 Tag／Release 不動。

## 可用程度先說清楚

- **A：官方組**，可由啟動程式安裝官方 Windows 套件；尚待使用者 B580 實機驗證。
- **B：Kitchen XPU 原生實驗組**，啟動隔離、建置／安裝入口與嚴格預檢已實作，**目前未找到可直接取得的公開配套 Windows 原生 Wheel**。需要使用者已準備好的開發工具建置，或自行提供相符 Wheel 及 SHA256。沒有這些先決條件時 B 組會停止，不能說下載本測試版後兩組便都可直接跑。
- 不以 CPU／eager 測試通過當作 XPU 加速通過。不會為了原生核心降級整個 PyTorch，也不會自行安裝系統編譯器／SDK 或覆寫系統 DLL。

## 兩組與原有啟動方式

| 項目 | A：官方 | B：Kitchen XPU 實驗 | 原 Intel 啟動方式 |
|---|---|---|---|
| 啟動檔 | webui-user-intel-xpu-official.bat | webui-user-intel-xpu-kitchen.bat | webui-user-intel-arc.bat |
| venv | venv-xpu-official | venv-xpu-kitchen | venv-intel-arc（未改） |
| torch | 2.14.1+xpu | 2.14.1+xpu | 2.14.0+xpu（未改） |
| torchvision | 0.29.1+xpu | 0.29.1+xpu | 0.29.0+xpu（未改） |
| Kitchen | 官方 0.2.38 | 固定修改版 0.2.37 | 根 requirements 原狀 |
| 連接埠 | 7862 | 7863 | 原狀 |
| 設定／輸出／快取 | runtime/xpu-ab/official | runtime/xpu-ab/kitchen | 原狀 |

使用相同 PyTorch，是為避免同時改 Torch 與 Kitchen 導致難以判斷效果；原 Intel 啟動檔另外保留，可比較 2.14.0 與官方 2.14.1。

模型預設共用專案 models，包括使用者已建立的 junction／符號連結；也可在啟動命令後加 `--model-ref "完整模型資料夾"`。data-dir 亦分開，避免 params.txt 等資料互蓋；各自 data-dir 下以 Windows 原生 junction 連回專案 extensions。程式碼與 extensions 原始碼仍共用同一 Git 工作目錄，因此「互不影響」指套件／設定／資料，不是複製整套應用程式。比較期間勿更新共用程式碼或外掛。不要同時生成後比較速度，兩個程序仍共用同一張實體 B580 的顯存與算力。

兩組首跑各自複製根 config.json／ui-config.json／styles.csv，其後不互相同步或覆寫。輸出路徑強制初始化到各自目錄；其他初始設定包括原本儲存的本機 API 設定也可能被複製，請自行管理。所有此類產物及 venv 都不提交 Git。

輔助下載快取（例如 HF／WD14）各自獨立，所以首次使用可能額外下載；本機既有模型檔不複製。Torch constraints 也各自獨立，不共用 NVIDIA 的 tmp/constraints-torch.txt。

## A 組操作

完整關閉目前 WebUI，更新 neo-test 後啟動 `webui-user-intel-xpu-official.bat`。第一次建立全新 venv 並安裝套件，可能需要較久與額外磁碟空間。使用既有 bootstrap-python.bat 的專案 Python 3.13.12；不改動 NVIDIA 或舊 Intel venv。

成功預檢後顯示 `[XPU A/B verified]` 與版本／裝置／後端資料，再啟動 WebUI。資料保存在該組 `runtime-report.json`。

## B 組原生依賴：不能忽略的限制

核對來源：

- Kitchen fork：https://github.com/xiangyuT/comfy-kitchen-xpu
  - 固定 commit：c2b77e7229bcb1917a5bf3145dc45cbe8fc389a9
  - 純 Python wheel 0.2.37，不攜帶原生 kernel。
  - 該版本沒有 GitHub Release；公開 PyPI 查詢 omni-xpu-kernel／comfy-kitchen-xpu-runtime 亦未找到套件。
- 原生核心：https://github.com/intel/llm-scaler/tree/main/omni/omni_xpu_kernel
  - 固定 commit：49d2f8d074397c91f138f933e7d7d6ff033f1581
  - WHL_BUILD_INSTALL.md 註明 2026-10-09 加入 Torch 2.14 Windows 建置合同，但該組合仍未完成 Windows build／安裝驗收；歷史已驗收案例是 2.13／Arc Pro B70，不能當作 B580／2.14.1 通過。
  - Windows 2.14 合同：oneAPI 2026.1、oneDNN package 2026.1.0／native ABI 3.12.0、C++20。
  - 不下載或重命名 2.13、Linux、PTL-H wheel 來湊數。

### 路徑一：已具備開發工具時建置

先準備 VS2022 C++ Build Tools、Windows SDK、Intel oneAPI 2026.1 DPC++ 編譯器及配套 oneDNN 開發檔，依上述原生專案的 Windows 文件初始化 **同一個 x64 developer shell**。確認 `cl`、`icx` 能找到；然後在專案目錄執行：

```bat
build-intel-xpu-kitchen.bat
```

此命令使用 B 組自己的 Python／套件，固定來源 commit，在 B 目錄內下載原始碼及產生 Wheel；不安裝系統工具。只建置 BMG **core-only**，`OMNI_XPU_REQUIRE_CUTE=0`，不宣稱已整合 CUTE／Sol-Attn attention 加速。

若編譯器、oneDNN header／DLL、Torch API 或硬體有不相容，建置／預檢會停止，應保留完整錯誤紀錄。不能保證這個未驗收的原生組合能在你的電腦一次建置成功。

建置與預檢成功後，再執行 `webui-user-intel-xpu-kitchen.bat` 開啟介面。

### 路徑二：已有可信的匹配本機 Wheel

```bat
webui-user-intel-xpu-kitchen.bat --kernel-wheel "D:\wheels\omni_xpu_kernel-版本+torch214.bmg-cp313-cp313-win_amd64.whl" --kernel-sha256 "該檔案的SHA256"
```

Wheel 檔名只是第一關；實際載入還必須核對完整 Torch build 身份、原生 core AOT target、B580 與能力集合。SHA256 只驗證檔案身份，不是相容／可信度保證。

B 組成功會紀錄 kernel／Kitchen 來源 SHA 與 Wheel hash，並且：

1. 要求 torch 2.14.1+xpu，且 Intel XPU 可用。
2. 僅接受本次使用者 B580 裝置；其他 Intel GPU 需另行審查。
3. 要求原生 kernel 的 __torch_version__ 與當前完整版本相同。
4. package target 及載入的 core AOT target 都為 bmg。
5. 要求原生 XPU backend 可用且有 quantize_int8_rowwise 能力。
6. 強制選用 XPU backend 做 INT8 量化 smoke test，檢查 dtype／形狀／有限數值與反量化誤差；不能藉由 eager 回退過關。

個別模型／算子在通過 smoke test 後仍可能依形狀與 dtype 使用 eager，這是 fork 的正常 dispatch，不代表整張圖或所有運算已加速。兩組保留同樣的 PyTorch SDPA／現有 XPU 注意力分塊，不開啟 CUDA-only Sage／Flash 或缺少支援的 INT8 attention。

## 實作與驗證

- 新增標準函式庫的 profile helper 與 entrypoint，不在普通 NVIDIA／Intel 啟動路徑執行。
- 用 subprocess 參數清單保留含空格路徑，不透過 shell 插入 URL／檔案路徑。
- 兩組使用各自 pip 安裝約束；B 的 .37 pin 只存於其 runtime requirements，不覆寫根 .38。來源基線若改變，要求重新審查，不自動硬套舊 fork。
- 清除可跨環境重導 pip／Python 的繼承變數；launcher setlocal 不改父 shell。共用擴充安裝階段以 lock 序列化。
- 拒絕會破壞比較隔離的 port／config／data-dir／CUDA-only 或批次更新外掛參數。設定可在各自介面調整。外掛若自行把設定寫在共用程式碼目錄，該部分仍屬共用，不能保證第三方外掛任意行為完全隔離。
- 原始碼 checkout 固定 SHA；有本地修改時停止，不覆蓋。
- 新增 12 項 portable 回歸測試：環境不變性、獨立 cache／設定／輸出、模型共用、安裝約束隔離、錯誤 Wheel／ABI／AOT／缺能力拒絕、缺編譯器早停、全新 source checkout 與 dirty source 保護。
- 完整 unittest 91/91 通過、0 skip；本輪使用 Linux／Python 3.12／torch 2.14.1+cpu。
- Kitchen 固定來源在 CPU 上成功匯入，Forge 使用的 18 個 ck 屬性及 tensor imports 皆存在；CUDA disable 呼叫相容。CPU 下回報 xpu=False/eager=True 是預期行為，不當作 B 組通過。
- Python 語法與 CRLF-aware diff 檢查通過，CPU CI 額外跑 profile -O 檢查；遠端結果記於 ai-work-log Issue #5。

**未做**：Windows .bat／venv 首跑、Windows 原生 Wheel 編譯、oneDNN DLL 載入、B580 smoke／生成、完整 WebUI、A/B 效能與品質比較。A 組及 B 組都不得宣稱已實測；B 組還有明確的原生建置／配套依賴缺口。

## 公平比較

先 A，完全關閉後再 B。保持模型、VAE、seed、解析度、步數、取樣器、CFG、batch、HR 與 ControlNet 設定相同。先各做一次暖機，再記錄至少三次耗時／顯存／錯誤與成圖。SDXL、Qwen 或不同量化格式應分開比較；若某流程未呼叫修改版的原生算子，沒有加速並不意外。

若要回退，直接使用原 webui-user-intel-arc.bat；無須刪除或重建原本的 venv。A/B 的各自 runtime-report.json 與完整 console log 可用於後續除錯。
